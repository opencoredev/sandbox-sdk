# Independent sandbox provider benchmark

The v2 harness measures the SDK, guest hardware, guest performance, deterministic agent work, and lifecycle cost. It keeps failures and raw observations. It makes no combined provider ranking. `local` is a Docker reference baseline, not a cloud product. The `default` track compares provider defaults. The `same-spec` track records explicit size and template choices, with fingerprints showing actual resources and any remaining differences.

Build the SDK and run a small pilot before collecting publication data:

```sh
bun install
bun run --cwd packages/sdk build
# Load credentials privately into environment variables. Never enable shell tracing.
for f in ~/.config/sandbox-bench/*_KEY; do export "$(basename $f)=$(cat $f)"; done
bun bench --runs 2 --bursts 3 --concurrency 4 --provider-concurrency 1 \
  --run pilot-001 --out results/pilot-001
```

Output paths are relative to `bench/` through the root alias. Each output directory contains `results.json`, `results.md`, a self-contained `index.html`, `samples.ndjson`, and an `ownership.json` cleanup journal. Reports checkpoint after each sandbox; raw observations append after each scenario as a crash journal. At successful finalization, `samples.ndjson` is rewritten to exactly match `results.json.samples`, including fingerprint backfills, final cost corrections, and burst aggregate rows. Treat interim NDJSON as provisional. Do not reuse a run ID or output directory for a new collection. The harness never prints credentials. Run reports can contain public egress IPs, native sandbox IDs, and hardware identifiers; review before publication.

Use the same SDK commit and harness commit for every provider in a published comparison. A pilot is a harness check, not publication evidence.

## Merge collected results offline

Run `bun bench merge` from the repository root to build `bench/results/publication-final/` from the seven collected publication runs. It writes `results.json`, `samples.ndjson`, `results.md`, and a self-contained `index.html`. The merge does not call providers or collect new data. Generated publication datasets remain local under the existing results ignore rule.

For other v2 runs, pass result directories explicitly. Paths are relative to `bench/`:

```sh
bun bench merge results/run-a results/run-b --out results/merged --seed 45
```

`--exclude run-id` can be repeated. The aborted `publication-001` is always excluded. Duplicate run IDs, invalid schemas, different JSON/NDJSON samples, and an output path equal to an input are rejected. Existing output files with these four names are replaced.

The merged schema is `publication-merge-v1`, documented in `results.json.schema` and the report. Every included observation remains, including failures, blocked dependencies and skips. `sourceRunId` and zero-based `sourceSampleIndex` identify its original row. `sourceIteration` preserves the original iteration; `iteration` is reassigned per provider across source runs and burst namespaces. Scenario rows from one sandbox iteration share the new identity. Main, snapshot and burst summaries stay separate. Tracks, requested sizes and templates also have separate summary groups. Historical rows without a track belong to `default`. Do not pool older SDK-inclusive cold measurements with the SBX-53 bare-readiness method.

Distributions and confidence intervals are recomputed from successful samples with the existing statistics code. Raw success rates remain beside rates excluding specifically classified account-limit and client/third-party failures; skips and blocked rows have separate counts. Unknown operation causes remain operation failures. `network-mbps` stays in the data but is labelled not comparable, without a chart or rank. Source commits, flags, regions, seeds, host data, pricing, budget diagnostics and cleanup records remain attached to each source. The default report explicitly discloses the budget-fix top-ups and the discarded run.

Run-cost estimates sum only known `sandbox-lifetime` estimates, which already include restored lifetime. They do not add the overlapping scenario allocations. Missing lifetime costs stay unknown, and the report shows known subtotals plus unpriced counts in native currency. Boxd remains EUR.

## Select equal publication attempts

Pass `--policy path/to/policy.json` to `bun bench merge` to apply the publication targets: 100 main attempts, 30 workload and snapshot attempts, and three burst cohorts per size. The policy contains `replacements` (`provider`, `suite`, `scenario`, `sourceRunIds`) and `notRun` (`provider`, `suite`, `scenario`, `reason`) arrays. A scenario ending in `/*` matches its burst member and aggregate rows. Use replacement rules to select only the fresh pause/resume sources and fresh Boat bursts. Document unsupported capabilities and account limits in `notRun`; these are not provider failures.

Policy rules accept an optional `track` (`default` when omitted). Attempt targets and counts are independent per track, and an old default-track replacement or not-run rule never applies to same-spec.

Selection drops classified account-limit and client/third-party failures, then keeps the first N attempts per track, provider, suite and test in `startedAt` order. Ties use source run ID and original sample index. Provider-operation failures count as attempts. Blocked and skipped rows do not. Selecting burst cohorts also selects their associated member rows. Original source files remain unchanged, and the report records selection removals and every source date/configuration.

Run `bun bench attempts results/publication-final-v2` to print every required provider/test count and fail on missing or excess attempts without a documented not-run reason. It also checks the three phase fields on successful pause/resume samples. Pause/resume failures retain whichever phases completed; the total sample value remains elapsed time. Use `--omit-network-download true` for performance top-ups that must omit the optional CDN download while retaining CPU, memory, disk and TCP probes.

Normal jobs enter a round-robin provider queue per iteration. Independent providers run concurrently within the global limit. A provider holds its slot through cleanup. Scenario groups are shuffled deterministically for each iteration, using the same order across providers. Dependencies remain ordered: fixture upload/install → dev server → preview → edit. Cold comes first, fingerprint follows, and destruction comes last. No warmup or outlier is discarded.

Bursts intentionally override the normal per-provider iteration limit: K creates start together, record individual cold/readiness times and failures, retain all VMs until the cohort finishes, then destroy them. Cohorts run in isolation from normal work and from other burst providers. K is capped by the global concurrency limit and account limits (defaults: boxd 50, Instabox 25, E2B 20, Archil 20 (its Developer plan cap), Upstash/Freestyle 10, Luxor 5, others 10). These are conservative admission settings, not verified account entitlements. Check the actual account before raising them. A cohort above its cap is skipped, not silently reduced.

The dollar guard reserves a conservative timeout-based estimate at admission. Estimates settle against measured lifetimes and observed allocation; overlapping restored VMs add their own lifetimes. Failed creates count toward the sandbox budget. Unknown costs reserve the admission estimate and stop further creation. Credits, subscriptions and provider-side unknown-outcome charges cannot be enforced by this local estimate. Boat has the same budget controls as every other provider.

For publication, use 100 normal iterations and 30 workload iterations, serial within each provider. This gives useful p50/mean estimates; p99 from 100 samples is still unstable. Keep raw samples and CIs. Increase the global limit only after examining host-load counters.

```sh
# Run a pilot first and resolve its blockers before a publication collection.
bun bench --runs 100 --workload-runs 30 --bursts "" \
  --concurrency 4 --provider-concurrency 1 --seed 45 \
  --max-sandboxes 250 --max-dollars 10 --provider-max-dollars boat=2 \
  --run publication-001 --out results/publication-001

# Isolated burst-only collection: K creates can run together within this global limit.
bun bench --scenarios burst --runs 1 --bursts 10,25 --burst-cohorts 3 --concurrency 25 \
  --max-sandboxes 110 --max-dollars 5 --provider-max-dollars boat=1 \
  --run publication-bursts-001 --out results/publication-bursts-001
```

K=25 is skipped on accounts whose configured cap is lower. A burst above `--concurrency` is also skipped; its K is never silently reduced. Do not raise those caps merely to complete the table. Reconnect and pause/resume each target 100 attempts when supported; snapshot, restore and each agent workload target 30. One sandbox serves multiple scenarios, so these are not independent fresh-machine samples per workload. To isolate a workload, collect a separate run with `--scenarios npm-install` or another scenario name.

| `destroy`                          | Deletion requests only, retries retained; ownership checks and journal writes appear separately as `ownershipVerifyMs`/`ownershipPersistMs`; final listing verifies eventual deletion           |

The fingerprint records CPU model and flags, affinity-aware `nproc`, cgroup CPU quota and memory limit, host MemTotal, df/lsblk capacity/type, virtualization probes and readable DMI, kernel/distro, user/uid/sudo, installed tools, Python version, steal time, and optional no-key ipinfo egress IP/org/region. A failed IP lookup is null. A provider may expose host CPU/RAM/disk information beyond its allocation; prefer cgroup limits and inspect raw fields. Default Docker reference size is `medium` (2 vCPU / 4 GiB); its shared backing filesystem size is not a dedicated disk allocation.

Guest performance uses the same rootless CPython script everywhere. It never installs system packages. Images need `python3`; workload images also need Node/npm/git. Missing tools remain a measured failure rather than a fabricated comparable score. The pip workload needs no `venv`, `ensurepip`, sudo or system-package changes.

- CPU: fixed 1,000,000-step 32-bit LCG, iterations/second, single process and process pool sized to `ceil(min(nproc, quota))`, capped at 64. Worker startup counts in all-core performance. Python version differences affect the score and must be disclosed.
- Memory: 64 copies of a 16 MiB bytearray, decimal MB/s. This measures runtime copy throughput, not DRAM-only bandwidth.
- Disk: 64 MiB sequential write + fsync, sequential read, and 256 random 4 KiB operations at queue depth one. Random writes fsync each operation. Reads are buffered and may be cached; no root or O_DIRECT is used. Do not describe these as raw hardware IOPS.
- Network: exactly 25,000,000 bytes from `https://speed.cloudflare.com/__down?bytes=25000000`, including TLS, using a fixed User-Agent; decimal MB/s. TCP latency is the mean of five connects to `1.1.1.1:443`. HTTP denial and byte-count mismatches are failures.

The HTTP edit loop verifies served file changes, not browser rendering or React HMR execution. Network location, shared tenancy, provider image caches, package caches, and filesystem caching remain confounders. The raw host counters include loadavg, per-core ticks, process CPU and `/proc/net/dev` before/after each sample so client bottlenecks can be investigated.

## CPU sustained, CPU burst and burst survival

Three scenarios for how a provider holds up under load, beside the readiness bursts. None is part of the CI benchmark. They are the stress suites: each runs only when named in `--scenarios`, never by `all`, and only beside the other stress suites, so a run is a stress run by its plan alone (`--scenarios command,cpu-sustained` is refused). A run naming a stress suite collects no readiness bursts; a cohort suite needs `--bursts`.

**`cpu-sustained`** runs as normal iterations (create, fingerprint, the probe, destroy). `probes/cpu.py` runs the same CPython 32-bit LCG kernel as `perf.py`'s `cpu-single`/`cpu-all`, from a fresh random seed for every run, for fixed work: 20 segments of 10,000,000 steps on one process, then the same on `ceil(min(nproc, quota))` workers (max 64) started together. Workers are plain `fork()` children reporting over pipes, so the probe needs no `/dev/shm` (unlike `perf.py`). Before the run the harness writes the script into the guest and reads the guest clock; the run itself is one short command (`python3 /tmp/bench-cpu-<seed>.py run SEGMENTS STEPS CORES SEED`), and the clock is read again after it. Rows: `cpu-sustained` (probe wall time, full output in `details`), `cpu-sustained-single` and `cpu-sustained-all` in steps/s. Their `details` record the seed, seconds, each segment's rate, `consistency` (`minOverMedian`, the slowest segment over the median segment, so one stalled segment shows wherever it falls; `lastOverFirst`, the last quarter's mean rate over the first quarter's, below 1 when the guest slowed by the end), the exec on the host clock (`exec`, from just before dispatch to its return) with the guest clock's drift between the two reads (`clockDriftMs`, a diagnostic), and the CPUs the guest sees: visible, affinity set and cgroup quota, with `guestVcpus` = affinity capped by quota. On the CPUs published so far (9-20 M steps/s) each phase takes roughly 10-25 s. Collect it in its own run: `--scenarios cpu-sustained --runs 30`.

A probe row fails unless its output passes every check: the run's seed, work and worker count; every process's final LCG state equal to the harness's own value for that seed (so a reply recorded on an earlier run fails); segment durations that add up to each phase's time; guest wall-clock spans that match the timers; every all-core worker starting and ending inside its phase; no rate above 1e9 steps/s (CPython does 9-30 M), per process and per worker over the all-core phase; and phases that fit inside the exec the host timed. These checks reject wrong, stale and impossible replies. They do not prove the guest executed the work: the LCG has a closed form, and a provider controls its guest and what it prints, so a dishonest guest could compute the checksum and report plausible timings.

**`cpu-burst`** and **`survival`** are cohort suites like `burst`: K sandboxes created at once (K from `--bursts`, repeated `--burst-cohorts` times), isolated from normal iterations and from other providers, with the same account caps and admission rules. They run only when named in `--scenarios`. A run naming only cohort suites collects no normal iterations; `cpu-sustained` named beside them runs as normal iterations first. Readiness bursts run when `burst` is named, or when no stress suite is. A K listed twice (`--bursts 10,10`) runs two distinct cohorts. Each member is created and fingerprinted, then waits until every member is ready or has failed, so the work starts together.

- `cpu-burst`: every member stages the probe (script upload, guest clock read) before the common start, then runs it with 4 segments of 10,000,000 steps. Member rows: `cpu-burst-K/cold`, `fingerprint`, `cpu`, `cpu-single`, `cpu-all`, `destroy`, `sandbox-lifetime`. The aggregate `cpu-burst-K/all-complete` (ms) runs from the common start to the slowest member's exec return, each timestamped as the exec returned and before any row is written; it is a sample only when all K completed. Its `details` hold the per-sandbox spread for both phases (nearest-rank p50/p95, min/max, mean, max/min and coefficient of variation) and `overlap`, a proven lower bound on how long every member ran each phase at once (below). Each member's `cpu-single` and `cpu-all` rows record `exec`, the member's exec on the host clock from just before its dispatch to its return, `seconds`, the phase's length on the guest's monotonic timer, and `clockDriftMs`, the change in the guest clock's offset from the host between a read at staging and a second read after the run. `clockDriftMs` is a diagnostic only: no guest wall clock places or judges anything.

  The overlap bound uses only the host clock and each guest's own phase lengths. A member dispatched at `d` whose exec returned at `r` ran its single-core phase (length `s`) and then its all-core phase (length `a`) inside `[d, r]`. So its single-core phase started no later than `r - a - s` and ended no earlier than `d + s`, and its all-core phase started no later than `r - a` and ended no earlier than `d + s + a`. Every member was running a phase at least from the latest of those latest starts to the earliest of those earliest ends, however any guest clock stepped. `overlap` records that span per phase (`provenMs`) and its share of the median member's phase length (`provenFraction`), the spread of the members' dispatch times (`dispatchSkewMs`), and `ok` when the unrounded fraction is at least 0.8 for both phases. A member whose two phases are longer than its exec contradicts itself and makes the bound `inconsistent`. The bound is conservative: exec overhead (dispatch latency, interpreter start, the reply) counts against it, so a cohort that ran together can still fall short, and is then left out rather than modelled. A cohort that is not `ok` is not shown to have run its CPU work together.

- `survival`: each member sends `cat /proc/sys/kernel/random/boot_id` every `--survival-heartbeat-ms` from the common start and at the window's end (`--survival-window-ms`; 21 heartbeats for 5 minutes at 15 s), each bounded by the interval. A reply must be a boot ID. After a missed heartbeat the harness makes one exact read-only native lookup, bounded the same way. Exact lifecycle evidence decides: the member died if the sandbox is absent or terminal or its native state is dead (exited, stopped, failed and similar), and did not if the lookup finds it in a live state, whatever the exec error said. The SDK's `not_found` decides only when no lookup answered. A changed boot ID is a death too (a reboot loses state). Any other miss makes the member unresponsive, even if it recovered. A slot that passes while a miss is being handled is recorded as skipped, never sent late; so is a slot whose timer woke past its grace (a quarter interval, at most 250 ms), which is no verdict rather than a miss. Every heartbeat and lookup ends by one cohort deadline (cohort start + create + fingerprint + window + 2 heartbeat bounds), checked again after each wake, which keeps the cleanup steps inside the admission reserve. A member survived only if every slot answered, through the one at the window's end; a window the deadline cut short is no verdict. Member rows: `survival-K/window` (ms; a sample when it survived, else a failure carrying the evidence that decided the verdict), with every heartbeat and the verdict, including that evidence, in `details`. The aggregate `survival-K/cohort` (unit `sandboxes`) counts survivors, with `attempted`, `createFailed`, `died`, `unresponsive`, `interrupted` and `noWindow` in `details`. An interrupted run's unfinished windows are skipped, not failures.

Create failures in both suites keep the failure taxonomy. Besides the existing rules, a `cpu-burst` or `survival` create, or an unresponsive window, is `provider-account-limit` only with a typed signal. An HTTP status decides whenever one was recorded: only 429 is a quota refusal, 5xx is the provider's, and the SDK's code never overrides it (an adapter that maps a 507 to `quota` still records a provider failure). SDK code `quota` counts only when no HTTP status was recorded. Wording and other codes stay the provider's, including Daytona's `invalid_argument` (the readiness-burst rule for it is unchanged). A heartbeat whose reply or error arrives after its deadline is a timeout, whatever it says: its code and status are not kept, and publication ignores them on any miss recorded as timed out or as later than `heartbeatTimeoutMs`. An unresponsive window carries its deciding miss, by precedence: a proven death first (it carries no heartbeat error code and is never an account limit), then the first miss that proves a provider failure (HTTP 5xx, or SDK code `provider` or `unavailable` with no HTTP status), then the first typed quota refusal, then the first miss. It counts as an account limit only when no miss proved more than a quota refusal. Boat's quota-wording rule does not apply inside these cohorts. Admission reserves, per member, create + fingerprint + staging + probe for `cpu-burst`, and create + fingerprint + the window + 2 heartbeat bounds for `survival`, each plus three cleanup steps: drain, the live ownership check and the delete. A stress sandbox's cleanup inside its iteration ends by its reserve, a late-settling create's included: a delete is retried only while a whole attempt (check and delete) still fits. One still there when the reserve runs out is listed in `cleanupReview`, its provider admits no more sandboxes that run, and the run's final sweep retries the delete; it stays journaled for `bun bench reap --run ID` if that fails too. Cleanup past the reserve cannot be bounded, so it is priced instead. `budgets[provider].estimatedUSD` prices every sandbox from its iteration's start until it was first observed gone: an exact native lookup found it absent or terminal. A delete acknowledgment is not a stop. After one, the harness looks the sandbox up at once and then every 0.1-1 s, beside the iteration so no timing changes, for up to the step timeout (at most 30 s); once every provider's final sweep is done, each sandbox still unseen gets one more lookup. A sandbox never observed gone, whatever its delete returned, is listed in `openLiabilities`. All providers' budgets are priced to one cutoff taken after every sweep and lookup, just before the report is saved, so a sandbox one provider left live is priced through the time other providers spent cleaning up. An estimate over `capUSD` says so in the budget's `stop` note. The publication suites keep their published reserves and cleanup. Modal's hard lifetime covers a survival member; an explicit `--lifetime-ms modal=...` shorter than that is refused.

```sh
bun bench --scenarios cpu-sustained --runs 30 --bursts "" --run cpu-sustained-001 --out results/cpu-sustained-001
bun bench --scenarios cpu-burst --bursts 10,25 --burst-cohorts 3 --concurrency 25 --run cpu-burst-001 --out results/cpu-burst-001
bun bench --scenarios survival --bursts 10,25 --burst-cohorts 3 --concurrency 25 --run survival-001 --out results/survival-001
```

Merge stress runs into their own report, apart from the publication report, and give both to `site-data`:

```sh
bun bench merge results/cpu-sustained-001 results/cpu-burst-001 results/survival-001 --policy stress-policy.json --out results/stress-final
bun bench site-data --report results/publication-final --stress-report results/stress-final
```

Every field but `stress` comes from `--report` exactly as before, so adding a stress report leaves them unchanged. A publication report that includes a stress run is refused rather than filtered, judged by each source run's scenario plan, whatever rows selection left of it. `stress` comes only from `--stress-report`, which is refused if it includes a run that is not a stress run. `site-data` needs exactly one of `--stress-report DIR` or `--no-stress` (an empty stress section), so leaving out the stress report never empties a published section by accident. In `merge`, every row of a stress run takes the run's stress suite (`cpu-sustained`, `cpu-burst` or `survival`), its create, fingerprint, destroy and lifetime rows included. The attempt policy selects them by whole unit, a cohort (`<kind>-<K>` and cohort index) or a cpu-sustained iteration: a rule matching any row of a unit removes all of it, and for the cohort suites a superseded rule's `iterations` are cohort indices. No stress row is dropped for its failure class or a target count, so refusals stay as evidence. Stress removals are counted in `stressSelectionRemoved`, never in `selectionRemoved`. The `stress` section:

- `stress.observations`, `stress.runs[]` (`id`, `suite`, `samples`): the stress report's runs and rows; `stress.selectionRemoved`: its policy removals by reason.
- `stress.cpuSustained[]` per provider and allocation (`requestedSize`, `template`): `single` and `all` (`n`, `p50`, `p95`, `min`, `max`, `ciLow`, `ciHigh`, steps/s); `singleSeconds`, `allSeconds` (`p50`, `max`); `consistency.single`/`.all` and `trend.single`/`.all` (`p50`, `min` of `minOverMedian` and `lastOverFirst`); `guestVcpus` and `workers` (`value`, `count`); `attempts` (`successes`, `failures` by `accountLimit`/`clientNetwork`/`provider`, with a probe blocked by a failed create or fingerprint counted as that row's failure, `blocked`, `skipped`).
- `stress.cpuBurst[]` per `k`: `providers[]`, one per provider, allocation and work, with `cohorts` (complete: all K admitted), `completeCohorts` (all K finished), `excluded` (finished cohorts left out of `perSandbox`, by reason: `lowOverlap`, `invalidEvidence`), `incomplete` (`cohorts`, `members` admitted below K, never pooled), `members` (`attempted`, `ready`, `completed`), `failures` by class, `perSandbox` (`cohorts`, `single`/`.all` spreads with `n`, `p50`, `p95`, `min`, `max`, `mean`, `maxOverMin`, `cv`) from cohorts that all finished with a proven overlap of at least 0.8 in both phases, `withinCohortMaxOverMin` (`p50`, `max`), `dispatchSkewMs` (`p50`, `max`), `allCompleteS` (`n`, `p50`, `max`). Publication recomputes each finished cohort's overlap bound from its members' rows (`exec` and `seconds`) and never reads the aggregate's stored `overlap` or any guest wall-clock time. A cohort whose members' rows are missing or unreadable (rows from before `exec` was recorded included), whose two rows for a member record different execs, or whose phases are longer than their exec is `invalidEvidence`; the rest are `lowOverlap` when the proven fraction is below 0.8 for either phase. `clockDriftMs` is never a reason.
- `stress.burstSurvival[]` per `k`: `providers[]`, one per provider, allocation and plan, with `windowS`, `heartbeatS`, `cohorts` (complete), `incomplete`, `attempted`, `survived`, `createFailed` (`total` and by class), `died`, `unresponsive`, `interrupted` (members whose window the run cut short or never started, once each), `invalidEvidence` with `invalidReasons` (count by reason), `windowFailures` by class, and `survivalRate` = survived / (attempted − account-limit and client create failures − interrupted − invalid evidence − account-limit window failures), from complete cohorts only. Each member's verdict and failure class are recomputed from its window's raw heartbeat records alone, with the runner's precedence (death, then provider failure, then typed quota refusal, then any other miss) and the same typed-signal rule; the row's stored outcome and failure class are never read. Create failures are classed the same way: from each cold row's raw outcome (HTTP status, then SDK code), never its stored `failureClass`. A member is `invalidEvidence`, left out of the rate, for any of: `unreadable` (details missing or malformed, including no recorded `heartbeatTimeoutMs`, or one longer than the interval), `plan-mismatch` (its window plan differs from its cohort's), `off-slot` (a heartbeat off its scheduled slot, or more heartbeats than slots), `bad-boot-id` (an answered heartbeat whose reply is not a boot ID), `late-reply` (an answered heartbeat whose reply arrived after `heartbeatTimeoutMs`), `verdict-mismatch` (the recorded verdict differs from the recomputed one). The runner judges a reply by when it arrived: one later than the heartbeat's deadline is a timed-out miss, however late the deadline's own timer fired.

The run report's "Stress planning estimates" table prices these suites from a pilot's own rows: CPU sustained as 30 dedicated iterations, and each cohort suite at K=10 and K=25 with the configured cohorts, by pricing each observed member lifetime on its own and averaging those prices, so minimum billed time, rounding and creation fees apply per sandbox, then multiplied by the number of sandboxes (the readiness-burst estimates `burst10`/`burst25` are priced the same way); a K above the account cap shows as skipped. It is separate from the existing totals.

## State survival and memory pressure

Two checks in `bun bench fairness` (same-machine track, one sandbox per provider, results in `<out>/<check>.json`). `--max-dollars N` reserves each provider's sandbox for the check's whole lifetime at list price and leaves out providers that would pass the cap. It is an admission estimate, not an invoice bound; each check also stops itself a minute before that lifetime so cleanup destroys the sandbox, including on adapters that take no lifetime.

```
bun bench fairness state-survival --providers e2b,upstash --max-dollars 3 --out results/fairness/state-survival
bun bench fairness memory-pressure --providers e2b,daytona --max-dollars 3 --out results/fairness/memory-pressure
```

Both work in a fresh directory per attempt. Every process they start writes its pid and its start time from /proc to a pid file, and they only ever signal a pid whose current start time matches that file and that is not a zombie. They use the image's `node`, else `python3`. A process probe reports a live process's pid and start time, `gone`, or `unknown` when /proc, the pid file or the process's stat could not be read; `unknown` is never counted as a loss. Boot ids and file hashes that are not well formed count as unread. A sandbox whose destroy failed, directly or in the attempt's label sweep, counts as gone only when a later delete succeeded or the provider's exact lookup finds it gone (a paused sandbox may not show its labels); otherwise the attempt reports `destroyed: false`. A sandbox the sweep found but whose create was rejected has no handle to look up, so a failed delete of one always reports `destroyed: false`.

**state-survival** writes a 16 MiB random file, starts an HTTP server that holds a random token and 32 MiB of random bytes in memory, and a shell worker with a 1 s heartbeat, all detached from the exec. The baseline must show the whole file and both processes alive. It SIGKILLs and restarts the server five times; the guest times each from the kill to the new child answering with its own launch nonce (`restart.medianMs`). A trial that found no previous server to signal is counted in `restart.startsOnly`, not the median. Where the adapter has pause and resume, it pauses, holds 60 s and resumes, then times from resume returning to the first command (`firstCommandMs`) and to the original server answering (`servingMs`, observed). When the server is confirmed gone it is started again; `serverRestarted` is true once that new one answers, and `coldServeMs` is the first command plus the guest-timed restart, a composed figure rather than an observed one. Missed heartbeats are bounded from the host times around the two snapshots, so a late answer widens the range instead of moving it. Verdicts: `in-ram` (file, server process, token and memory digest, and worker all survived, and the worker missed at least 80% of the hold's heartbeats even if every second outside the hold, plus 2 s for sampling, was frozen too), `kept-running` (all survived and the worker missed at most 20% at the widest bound plus the same 2 s), `cold-restart` (a new boot id, or both processes confirmed gone with the file intact), `files-lost` (directory or file confirmed absent where its parent could be read, or the file's hash changed), and `inconclusive` with a reason for anything in between, an unreadable file or process included. A pause, resume or first command that fails, times out or goes unanswered is kept as `failed` with its stage and error; that is not necessarily the provider refusing. Providers without pause in the adapter get `unsupported`; stop and start have no portable SDK call and are recorded as not run.

**memory-pressure** allocates random (incompressible) memory 64 MiB at a time up to 1.5 times the provider's advertised same-machine memory, in a detached process whose supervisor shell records its exit status, while the host polls for the boot id, progress and the liveness of the hog and its supervisor, through spells of silence, until the hog has ended. The baseline needs a valid boot id and a canary process with a fresh heartbeat. Only the recorded status or a new boot id is an outcome: `reached-target`, `process-killed` only when the supervisor recorded status 137 (SIGKILL; neither the hog nor Node or Python exit 137 on their own), `refused` when the hog printed its refusal and exited 3, and `sandbox-restarted` from a new boot id, and `sandbox-lost` when status polls fail and the provider's read-only exact lookup (at most every 15 s) says the sandbox is gone. A loss that follows a poll the host cancelled at its timeout is `inconclusive` instead, since an SDK may answer a cancellation it cannot confirm by destroying the sandbox. Everything else is `inconclusive` with its reason (no status by the deadline, no answer through the silence allowance, the hog and its supervisor gone with no status, any other exit status) and claims nothing about the provider. It records the most it held (`reachedEvidence` is `log` only from a log read in full after the hog's status was recorded, else `last-poll`, a lower bound). The hog launch must run to the end, or the check stops. Each health test checks the boot id itself and counts only when it started on the original boot; one that sees a new boot id makes the outcome `sandbox-restarted` and leaves the tests unrun. `oomKills` is the OOM count of the exec shell's cgroup before and after, which may not be the hog's: corroboration at most. The scope is `process` only when the canary is the same live process with a fresh heartbeat (a canary still alive but not yet beating is read again, a complete read at a time, for up to 8 s; `health.canary` and `health.canaryBeatAgeS` keep what the last read saw), `collateral` when it is confirmed gone, `sandbox` for a reboot or a lost sandbox, and null otherwise. `usableAfter` (a fresh 256 MiB allocation and a file write succeed) is measured only after a recorded status on the same boot: false for a lost sandbox or a test that ran to the end and failed, null when a test did not run to the end or was never run.

## Costs and statistics

`src/pricing.ts` contains official sources retrieved on 2026-10-19, resource rates, currency, increment assumptions, included disk, fixed plan sizes, and caveats. One-second rounding is an explicit estimate when a source does not publish an increment. Unstated creation fees are not invented. Subscriptions, credits, transfer and retained snapshot storage are excluded. Boat uses its default fixed VM rate. Upstash bills active CPU, so allocation × wall time is an upper bound; boxd RAM/disk allocations likewise overestimate used-memory/written-disk billing. boxd is EUR: reports keep EUR and use a conservative 2 USD/EUR only for budget admission, not a claimed exchange-rate quote.

Sample cost = billed seconds × observed vCPU/RAM/disk allocation rates, or the published fixed VM size/rate. Unknown resources yield null. Sandbox-lifetime totals include setup and idle time; do not sum them with scenario allocations or the performance submetrics. Performance-per-dollar divides each successful throughput score by the observed allocation's estimated per-second rate, then averages those ratios. It is an efficiency estimate (e.g. CPU iterations per currency unit), kept in the provider's stated currency. Local has zero marginal provider charge; its host costs are excluded and it is omitted from ratios that divide by zero.

Distributions retain all successful raw values and report nearest-rank p50/p95/p99, mean/min/max, population standard deviation, and deterministic 2,000-resample percentile bootstrap 95% intervals for p50 and mean. Failure counts remain in every summary. Success rate uses a Wilson 95% interval over successes + independent failures; skips and blocked dependencies are counted separately. Empty distributions are null, never zero or NaN. A small pilot validates the harness; it cannot rank providers reliably.

## Cleanup and recovery

Every created VM carries `sandbox-bench-run=<run ID>` in addition to the SDK label. Creation arrivals are tracked before SDK initialization; late arrivals receive ownership checks before deletion callbacks. Each iteration drains timed-out work before releasing its slot. Destruction runs in `finally` and retries. Snapshot deletion uses narrow provider-native hooks because the SDK has no common snapshot-delete method. Daytona snapshot creation uses its native nameable method: the harness journals a run-owned name before calling it with a bounded 600-second completion budget. The SDK wrapper also retains its generated name in errors, but cannot journal that name before submission. This path difference is disclosed in report methodology. Only IDs created by this run are journaled. Final cleanup checks both the run label and ownership journal, including snapshots. It polls the exact run label for up to 30 seconds (bounded by `--timeout-ms`) so asynchronous deletion can disappear from listing before reporting leftovers. Daytona snapshot listings receive the same bounded wait, scoped to each owned source. Snapshots carry a durable `snapshotProof` with the verified source ID, run label, SDK marker and verification time. Cleanup removes restored sandboxes first, then snapshots, then their sources. In-use snapshot deletion conflicts receive bounded backoff retries.

```sh
bun bench reap --run pilot-001 --out results/pilot-001
```

Run `reap` with the same environment the run used: the same keys and tokens, and the same endpoint, region, team, project, Docker socket and Modal profile variables. The run's `ownership.json` keeps no connection details, only a fingerprint per provider (16 hex characters of a SHA-256 over the provider's whole resolved connection, credentials included, and over what the provider's SDK reads from the environment itself: `VERCEL_OIDC_TOKEN`, `BOXD_REGION`, Railway's endpoint variables, and Boxd's and Tenki's endpoint variables when no endpoint is passed). Every provider the bench builds has one:

- local: the Docker socket the adapter uses (its `dockerHost` option, then `DOCKER_HOST`, then `/var/run/docker.sock`) and the `ID` the daemon behind it answers on `/info`, read at run start and again at reap. A socket path that now leads to another daemon differs, and a reap whose `/info` read fails skips local.
- Modal: the connection Modal's SDK resolves (`ModalClient`'s profile): server URL, tokens and Environment from the adapter's options, then `MODAL_*` variables, then the profile `MODAL_PROFILE` names in `MODAL_CONFIG_PATH` or `~/.modal.toml`. Building the client makes no request. If it cannot resolve a connection, Modal is skipped.
- memory and agentos run inside the bench process, so they have no connection to choose and fingerprint as a constant of their name. A reap passes them when the journal has that constant or, for a truncated journal, none.

Reap builds each adapter from its own environment and reads through it only when its fingerprint matches the one the run journaled. A provider whose fingerprint differs, that the journal has no fingerprint for, or that the bench has no connection model for, is skipped before any request, its journal entries are kept, and reap prints `SKIP <provider>: <reason>` without any value and exits nonzero. Journals written before fingerprints, which kept endpoint text, are refused. Clean up those runs' sandboxes in the provider's console, then delete the journal.

A run refuses to start when `--out` holds another run's `ownership.json` that still lists sandboxes, snapshots or Apps, because starting would overwrite it and that run's reap could no longer find them. Reap that run first, or choose another `--out`. `--force` starts anyway and overwrites the journal. A journal of the same run ID, an empty one, or one that does not parse is overwritten as before. An `--out` that already has a `run.json` is refused whatever the flags.

Reaping requires an explicit run ID. It checks exact label equality even if an adapter returns extra list results. Persistent snapshot recovery requires the matching output journal, recorded source ownership proof, and live snapshot identity/source metadata. The source sandbox may already be gone. Legacy entries without recorded proof require manual review. A journal from another run is refused. Without the original journal, only labelled sandboxes can be reaped, and only on the in-process providers (memory, agentos), since there is no fingerprint to check the others against; do not delete account-wide snapshots. A run writes its journal, fingerprints included, before its first create. If native creation fails before ownership metadata can be attached, the SDK may return `outcome_unknown`; inspect that provider's account rather than assume label-based discovery is complete.

SIGINT/SIGTERM stop admission and cancel signal-aware operations, then run normal cleanup. Do not use SIGKILL unless necessary. A provider outage can prevent deletion: a nonempty `cleanup.remaining`, cleanup error, or ownership journal is a blocker. Re-run scoped cleanup after recovery. Never use an account-wide delete because other agents use the same keys.

## Publication fairness updates

`--burst-cohorts N` repeats every configured burst size N times (default 3). Each aggregate carries its cohort index in `iteration` and `details.cohort`; cold samples have a unique iteration within that size. Three K=10 plus three K=25 cohorts require 105 sandbox attempts per provider, so the burst command reserves 110. Account and dollar caps still apply; a blocked admission is reported rather than silently reducing K. Three cohorts validate a distribution but are insufficient for a stable tail estimate; use more cohorts only within explicit account and spend budgets.

The default track uses provider default allocations and images, with the local Docker reference at medium size. The same-spec track uses the supplied per-provider sizes and templates. A track label alone does not establish equal hardware. Publish the hardware table beside timing results. Image, dependency, CDN and filesystem caches remain uncontrolled. Workloads on the same sandbox share installed files and process state.

A failed lifecycle transition marks later scenarios with outcome `kind: blocked` and `blocked_by: <scenario>`. App prerequisite failures propagate similarly. These rows appear separately from skips and independent failures; success-rate denominators include only successful and independently failed attempts. Latency distributions contain successful values only. Every expected guest performance metric receives a failure row when the probe fails, times out, returns invalid JSON, or omits that metric.

Cold and create-from-snapshot use the client monotonic clock immediately before `adapter.create` and stop after a bare `adapter.exec("true")` succeeds. Ownership is durably recorded before the bare command using a synced temporary file, atomic rename, and directory sync. `ownershipPersistMs` records that host interval and is excluded from cold and burst headline values. SDK handle initialization follows readiness. `adapterCreateMs` stops at the create return, `firstCommandMs` covers the bare command, and `coldMs` is the headline. `sdkReadyMs` covers create through the fully initialized SDK handle and is reported separately. `firstCommandOKMs` starts earlier, at iteration admission before host sampling and budget work. Burst all-ready uses the last member's bare-command endpoint, even when SDK setup finishes later. Failed bare commands retain failure rows and owned resources for cleanup.

Fixture preparation and uploads are separate `npm-install-prepare` and `tool-replay-prepare` rows, outside the headline workload windows. Preparation failures remain failures; the workload and its dependents become blocked rows.

File payloads are prepared once before scheduling. Reconnect preserves the previous handle if attachment fails; successful reconnections defer old-handle cleanup until after destruction because providers cache clients by sandbox ID. `preview-provisioning` measures public URL provisioning separately from `dev-server`. Each `preview-first-byte` row is a single HTTP attempt through its first nonempty chunk; up to three attempts retain failures separately. Reader cancellation and the 500 ms gap between attempts are outside that row’s timing. The edit loop depends on successful provisioning/start and, when collected, a successful first-byte attempt. `snapshot` measures only the native API; `snapshot-setup` exposes cleanup-client loading and durable journal preparation, and `snapshot-total` includes that setup and post-API journal work. Cost projections use the total, not a sum of overlapping snapshot rows.

Reports include configured provider regions, collection start/end, repository/harness/SDK git commits, a dirty-tree indicator, SDK/runtime versions and optional client public-egress geography from ipinfo. The SDK/harness commits identify the latest commits touching their respective directories; the repository commit identifies the complete checkout. A failed location lookup is null. Offline library consumers do not perform this lookup. The client-headroom section summarizes normalized load, host CPU busy fraction and network byte rates during each provider’s samples. Every raw sample has a `headroom` object and a high-load flag when load1/logical CPUs is at least 1 or measured host CPU busy fraction is at least 90%. Raw counters remain available. Overlapping windows and unrelated host traffic prevent attributing these counters solely to a provider; do not sum their traffic rates.

Percentiles use nearest rank. p50 and mean intervals use 2,000 seeded bootstrap resamples; independent success rates use Wilson 95% intervals. At n=100, p99 depends on roughly the two slowest observations and remains unstable. Publish raw data, counts, failures and blocked dependencies rather than presenting a precise tail ranking. Costs remain estimates with per-provider source retrieval dates. EUR and USD remain separate; subscriptions, credits and excluded charges are documented in the pricing table.

These additions extend schema v2: `metadata`, `providers[].configuredRegion`, `samples[].headroom`, blocked outcomes, and `summaries[].blocked`. Consumers must handle the new outcome variant. Older v2 pilot reports lack these fields and are historical artifacts; v1 compatibility is unchanged. The earlier pilot predates these fairness fixes and has not been rerun on cloud accounts.

### Allocation contract for site-data consumers

Every `site-data --track ...` export contains `track` at the root and on every provider. Render `providers[].requestedAllocation` beside `providers[].measuredAllocations`:

- `measuredAllocations` contains every distinct source and restored fingerprint allocation as `{cpu, memoryGiB, diskGiB}`. An empty array means allocation was not measured.
- `equalSpec` is true only when no restore allocation mismatch was detected, at least one fingerprint exists, and **every** fingerprint has exactly 4 vCPU and usable memory between 7.6 and 8.4 GiB, inclusive. - `allocationVerification` contains `verified` (true/false for a known provisioned allocation with measurements, otherwise null) and `mismatches` (human-readable reasons). `pricingAllocation` is the compute allocation actually priced. Explicit sizes must agree with every fingerprint: CPU exactly; usable memory must not exceed provisioned RAM and may fall below it by at most the larger of 5% or 96 MiB for kernel overhead. Conflicts suppress `hourly` and `perVcpuHour`; absent fingerprints produce null prices. Known template/default resources come from `src/provisioned-allocations.ts` and must agree with fingerprints before pricing. Prices use provisioned RAM rather than kernel-usable RAM. Luxor has no documented default CPU/RAM, so its unspecified default still uses measured resources. Restored fingerprints participate in every safeguard, and an allocation-mismatched restore latency remains recorded as a failure instead of ranking.

The root `allocations[]` repeats this evidence per provider/track as `requested`, `measured`, `equalSpec`, and `verification`. Each provider's `hardware` view remains descriptive; do not use its first/mode observation to override these safeguards. A false `equalSpec` can still have a valid price for the actual allocation (for example, boxd 4/16).

Restores omit size overrides and inherit their snapshot's allocation. `restore-fingerprint.details.verification` records source and restored resources, `matches` (null if the source fingerprint is unavailable), and mismatched dimensions. CPU must match exactly; usable memory and disk allow 5%. A mismatch is a failed restore-fingerprint observation; its fingerprint and cleanup remain recorded.

A lifetime total or cost per task stays `null` unless every attributed sandbox has a complete lifetime amount of the same kind. Daytona and boxd bounded-window amounts have `scope: "window"` and separate subtotals; settlement alone does not prove full lifetime coverage.

`billedUSD` means provider-reported usage charges before credits, tax and plan minimums, not a net invoice. `meteredUSD` is separate: Boat explicitly returns list-price usage dollars; E2B uses actual execution milliseconds and allocated resources with published rates; boxd prices its meter at current account rates; Instabox reports each machine's running vCPU-seconds and memory GiB-seconds (`GET /v1/machines/{id}/usage`, readable after deletion), priced at its published rates. Archil's `billedUSD` is its own per-sandbox cost from `GET /api/sandboxes/{id}/usage` (updated about once a minute, readable for 90 days, before included allowances and prepaid credit; compute only). Superserve hourly charges and boxd billing activity are retained as account evidence, never divided among scenarios. Superserve's monthly summary separates charges, applied credits and expected invoice. Luxor and Freestyle have no verified billing endpoint. Styne has none per sandbox: `GET /v1/run/usage` reports the account's running seconds and cost per day, so Styne costs are estimates at its published per-size rates.

A task means one distinct sandbox lifetime. Whole-sandbox charges belong to its `sandbox-lifetime` scenario, including burst variants, or its sole scenario when only one exists. Shared commands, files and other operations have no separate bill and retain `null` costs. Failed attempts with an ID are included; samples without IDs are counted separately and cannot be priced. Journal-only IDs and shared sandboxes without a lifetime scenario remain unallocated. Snapshot storage, unrelated account activity and subscription minimums are not assigned to tasks. Recovering selected sandbox charges does not establish the full benchmark invoice.

Boat's [machine documentation](https://docs.boat.dev/machines) lists 50 GB for the default machine as the maximum size of user files, excluding the operating system and pre-installed tools. The pilot measured a 68.58 GiB filesystem. Site exports keep those distinct: `requestedAllocation.provisioned.documentedDisk` carries the documented value, unit, scope and source, while `measuredAllocations[].diskGiB` carries the filesystem measurement. Boat disk differences do not affect allocation verification, restore eligibility or its fixed hourly price.

Every collection-plan command passes `--omit-network-download true`, matching the original publication. The public CDN download is not collected because the host rate-limits; guest `urllib` connection resets there do not measure provider performance. CPU, memory, disk and TCP probes remain enabled.

Daytona's `us` container account quota was raised to 250 vCPU, 500 GiB RAM and 2000 GiB disk on 2026-10-22. Daytona now runs every suite on both tracks, including same-spec snapshot/restore and K=10/K=25 bursts, through the shared plan commands with an account limit of 25. Earlier runs under the old 10 vCPU / 10 GiB / 30 GiB quota excluded those suites.

## Cost of one tool-replay task

Run `bun bench --providers e2b --scenarios cost --cost-runs 10 --bursts '' --out results/e2b-cost`, then `bun bench billing --report results/e2b-cost`. Use the same track, size and template flags as the matching latency collection. Merge that directory with the other suites before running `site-data`; merge reads its adjacent `billing.json`. Re-run billing and merge after delayed charges settle.

The cost suite defaults to 10 fresh sandboxes per provider. Each sandbox runs create, fixture upload, the same 100-call tool replay, and destroy. It performs no fingerprint, performance probe, snapshot or other workload. Fixture preparation and SDK setup contribute to the billed lifetime. Tasks run sequentially per provider even when provider concurrency is higher. Boat allows at most 10 tasks per invocation, with 6.5 seconds between tasks; use the scheduled collection windows for further batches. Both tracks include this suite.

Each site provider entry in each track exports `costPerTask: {usd, kind, source, confidence, n, settled}`. `usd` is the median cost of one completed sandbox task, or `null` when evidence is missing. `n` counts tasks supporting that median. A task must complete its replay and destruction. Native billing must identify every sandbox in the cost suite; mixed billed/metered evidence produces no median. `billed` means a provider-reported charge for each sandbox, before credits and tax. `metered` means provider usage multiplied by published rates. Account-wide charges are never divided among tasks. Per-sandbox window charges qualify only when the billing window encloses the complete sandbox lifetime.

Luxor and Freestyle use `estimate`: list price multiplied by each measured sandbox lifetime, using the matching allocation verified by fingerprints in the other suites. These estimates have low confidence and exclude subscriptions, credits and transfer. `settled: true` for an estimate means the task lifetime is final; it does not imply an invoice. Daytona charges can lag 48 hours, and boxd meters about 25 minutes. Pending values retain their current kind with `settled: false`; missing values have `usd: null`, `n: 0` and `confidence: "none"`. Superserve account-only billing remains unknown until per-task evidence is available.

Admission limits are coverage failures. Any budget-denied provider/scenario appears in `admissionStopped` in `results.json` and `results.md`, and the CLI exits nonzero. The collection script uses `set -e` to stop immediately. Documented capability/account restrictions belong in the collection policy, rather than being hidden by a budget stop.

A create/restore outer deadline remains a failed attempt even if native work later succeeds. During the bounded cleanup drain, its failure sample records `clockPhase` (`adapter-create`, `first-command`, or `sdk-init`) at the deadline and `lateSettlement` with the eventual native ID, reached stage, SDK code and allowlisted cause. Late IDs enter the durable ownership journal only after trusted admission and live ownership verification; other IDs enter cleanupReview. Native error bodies, headers and credentials are excluded. Work that cannot drain within the cleanup budget stops further scheduling and leaves recovery evidence.

Cleanup requires live ownership proof: a read-only provider listing must report both `sandbox-bench-run=<run>` and `sandbox-sdk=1` on the exact sandbox ID. A journal entry or an ID embedded in an error is insufficient. Rejected create IDs qualify for automatic recovery only when the adapter's create call throws an SDK `SandboxError` with the matching provider, `cause.operation="create"`, and `cause.admittedByThisCall=true`; live labels must still verify. Without this admission marker, IDs first enter quarantine; later live label discovery can establish ownership independently of the error.

Unverified IDs remain untouched. Failure samples expose `unverifiedSandboxId`, and `cleanupReview` in `results.json` and `results.md` records the provider, ID, resource kind and reason. Collection exits nonzero when review is required. `bun bench reap --run RUN --out DIRECTORY ...` prints unresolved entries and rechecks sandbox ownership. Fresh proof of the exact run and SDK labels releases a sandbox from quarantine; the harness journals it before normal cleanup. `cleanupReleased` records the original reason, release time and `live-run-sdk-labels` proof in JSON/Markdown, and resolved failure samples carry `ownershipReleased: true`. IDs that stay unproven remain for a human. Reap never deletes a sandbox by bare journal ID. Corrupt journals permit only discovery scoped by both ownership labels. Snapshot recovery requires recorded source ownership proof and a live snapshot lookup. Where the provider exposes the source ID, it must match the proof. A missing parent does not prevent recovery; missing recorded proof or unavailable snapshot metadata does. Cleanup keeps the source until restored sandboxes and snapshots are resolved.

Immediately after create/restore, missing or unreadable labels receive exponential backoff retries for up to 30 seconds, bounded by `--timeout-ms`. A visible different run label or SDK marker fails immediately. Live ownership checks and durable journal writes are excluded from cold and burst readiness clocks. Their elapsed times appear separately as `ownershipVerifyMs` and `ownershipPersistMs`.

A failed ownership listing does not prove absence. Cleanup and reap make an exact read-only native lookup for quarantined sandboxes. A definitive HTTP 404, Luxor gRPC 5, or a native `deleted`/`destroyed`/`terminated` state resolves the entry as absent without deleting anything. `cleanupResolved` records the original reason, lookup method, result, time and allowlisted status/code/state; the sandbox journal entry is removed. Empty lists, missing guest metadata, paused/stopped states, auth failures, rate limits, timeouts and server errors do not resolve quarantine. Persistent snapshots require their own proof even when a parent is absent. Original failure samples remain failures and carry `cleanupResolved: "absent"` when resolved.

Every exact lookup, snapshot read or delete, and cleanup or reap read goes through the connection of the adapter instance that created the sandbox: the endpoint, credentials and scope that instance resolved from its options and the environment, never the environment alone. A read sent to another endpoint, account, team or project answers 404 for a running sandbox, which would count as absence. An instance the harness did not build reads as `unavailable`. The run's `ownership.json` keeps only each connection's fingerprint, never its endpoints, scope or credentials: an endpoint can carry a credential in its userinfo, path or query. `bun bench reap` builds each adapter from its environment and skips any provider whose connection fingerprint differs from the run's (for example after `E2B_API_URL` or the key changed) rather than read elsewhere. Daytona's lookup and snapshot clients run in polling mode, so a read opens no event stream; no other Daytona path uses it.

Lookup latency is part of the evidence. A survival verdict after a missed heartbeat, and the moment a deleted sandbox is first observed gone (which ends its priced cleanup), both wait on a lookup. A slow control plane can push the lookup past its bound: the member is then unresponsive rather than dead, and the sandbox stays priced until a later lookup sees it gone.

Collection watchdogs should call the pure policy in `src/collection-watchdog.py` (`stop_reasons(report)` or JSON on stdin). During a run, sandbox reviews have `status: "checking"` while bounded deletion drain and exact lookup are pending; only `unresolved` entries (including legacy entries without a status) stop admission. A finished report with a remaining check also blocks collection. `cleanupResolved` and `cleanupReleased` are history, not stop conditions; a newer unresolved entry is never hidden by older history. The orchestration watchdog imports this policy.

### Baseten image

Baseten's default image (`baseten/base-image`) is Alpine, with musl and BusyBox, and the frozen toolchain needs glibc and GNU coreutils. Baseten runs only images in its library or pushed to the account, and a pushed image needs Baseten's sandbox agent as its entrypoint, so a plain registry import starts sandboxes that never answer. The realistic runs use `sandbox-bench-node22`, built once per account:

```ts
import { ImageBuilder, SandboxClient } from "@basetenlabs/sandbox";

const client = new SandboxClient({ apiKey: process.env.BASETEN_API_KEY ?? "" });
const builder = ImageBuilder.fromRegistry("docker.io/library/node:22-bookworm");
await client.images.push({ name: "sandbox-bench-node22", builder, memory: 8192, volume: 16384 });
```

The builder appends the agent copy and entrypoint. The main suite keeps Baseten's default image.

### Instabox

Instabox limits starts per account: 30 a minute on Pro, 50 on Builder (create, start, resume and wake; more is a retryable `429 rate_limited`). Collect each burst cohort as its own command, at least 65 seconds after the last, with nothing else creating Instabox machines meanwhile: `--bursts 10 --burst-cohorts 1`, three times, then the same for K=25. The same-spec track asks for `--size instabox=4:8192`, which is also Instabox's default.

Instabox blocks outbound HTTPS to public DNS resolvers (1.1.1.1, 1.0.0.1, 8.8.8.8 and 9.9.9.9 on port 443), so the `tcp-ms` probe, which connects to `1.1.1.1:443`, times out on every attempt. Other port 443 connections (GitHub, npm, Cloudflare) work, as does `1.1.1.1` on ports 80 and 53. The collection policy records it as documented not-run, so the harness writes no `tcp-ms` row for Instabox and notes the reason on the provider instead of counting a failure. If the probe ever returns a value, the harness records it and says on the provider note that the policy entry is stale. Remove the entry before merging, because the merge drops every row a not-run rule matches.

### Archil

Set `ARCHIL_API_KEY` (`~/.config/sandbox-bench/ARCHIL_API_KEY`). Keys are region-scoped: set `ARCHIL_REGION` when the key is not for `aws-us-east-1`, the default (others: `aws-us-west-2`, `aws-eu-west-1`, `gcp-us-central1`). The existence check and the billing collector read the same region's control plane.

Archil's default sandbox is 1 vCPU / 2048 MiB on `node:24-bookworm`; the presets are small 1/2048, medium 2/4096 and large 4/8192, and exact sizes take 1 to 32 vCPUs and 256 to 65536 MiB. There is no disk size: the root disk is about 1 TB and fixed, so `--size archil=cpu:memoryMb:diskGb` is refused before the run starts, and the same-spec track asks for `--size archil=4:8192`. The adapter has no snapshot, so the snapshot scenarios are skipped as unsupported.

Plans cap concurrent sandboxes: Free 5, Developer 20, Team 250 (https://docs.archil.com/administration/billing.md). The burst default is 20; raise it with `--account-limits archil=<n>` only on a Team account. A create refused for the cap is recorded as an account limit, not a provider failure. Free-plan sandboxes get deny-all egress, so the network scenarios need a paid plan. Lifetimes take 60 seconds to 24 hours, and both the lifetime and the idle timeout (default 1800 s) pause a sandbox instead of deleting it.

### Maritime

Maritime refuses about one create in three with `503 out_of_capacity` (2026-11-23), sometimes several in a row; the adapter tries again with a new idempotency key for up to 3 minutes, so a cold create under pressure includes that wait. The account's plan caps machines awake at once (25 on Growth), and the runner's burst admission assumes that limit unless `--account-limits maritime=<n>` says otherwise.

Maritime's billing source is per sandbox: `GET /v1/sandboxes/{id}/info` and every page of `GET /v1/usage?sandbox={id}`. A cost is final only when the sandbox has ended and has running intervals, every one with an end; the info's `costSoFarUsd`, which can be null once a sandbox ends, is not part of that, and a total that disagrees with the intervals is only noted. A sandbox with no interval is $0 only when the info says it ran 0 seconds at $0. The intervals are compute while awake (disk included); a paused sandbox's disk ($0.08/GB-month) is not in them, so Maritime stays out of the held-open idle diagnostic.

Snapshots are named by the run (`bench-<run>-<8 hex>`) and journaled with their source and the save's `Idempotency-Key` before `POST /v1/sandboxes/{id}/save`. A save whose answer was lost is settled by sending it again with that key and reading the snapshot, so a first 404 never drops the journal entry; an unsettled save keeps the entry, and its source, for `bench reap`.

### Styne

Styne's base template is its default size, 4 vCPU / 8 GiB with a 51 GiB root disk (`df` on `/workspace`), so both tracks run the same machine and the same-spec track asks for `--size styne=4:8192`. Styne prices by size, per second while running: $0.016 an hour for small (2/4), $0.032 for default (4/8), $0.064 for large (8/16) and $0.128 for xlarge (16/32), from 2026-11-20, after the plan's included hours. A paused or sleeping sandbox costs nothing. There is no per-sandbox billing API, so every Styne cost is an estimate.

Styne counts a sandbox's lifetime in running time and puts a sandbox to sleep when nothing started in it runs, which stops both the clock and the meter. The factory lifetime (`--lifetime-ms styne=...`, as for Modal) and each attempt's `timeoutMs` therefore bound billable time, not wall time; a held-open idle with nothing running inside does not count toward it.

Existence checks read `GET /sandboxes/{id}` only. Styne's `POST /sandboxes/{id}/connect` would wake a paused sandbox and move its end. An ended sandbox answers `410` with `state: "killed"` for a while, then `404`; both are absence. Snapshots are named before the request (`bench-<run>-<id>`) and journaled with their source, so a snapshot whose answer was lost is still found by name, and `GET /sandboxes/{id}/snapshots` lists a source's snapshots after the source is gone.

### Microsandbox

Two bench providers run on one adapter, one per compute tier: `microsandbox` is Standard (dedicated CPU) and `microsandbox-shared` is Shared. `bench/src/providers.ts` resolves both to `@opencoredev/sandbox-sdk/microsandbox` and pins `computeType` last, so no option can move a run to the other tier. The adapter checks the tier on every create and scopes `list` and `find` to it, and the bench adds a `sandbox-bench-tier` label that its sweeps also match: a Standard sweep never sees, deletes or prices a Shared sandbox. Both read `MSB_API_KEY` (`~/.config/sandbox-bench/MSB_API_KEY`) and optional `MSB_API_URL`.

Commands and files go through the `microsandbox` package (0.8.1), which needs its native platform package. Its published manifest omits the platform `optionalDependencies`, so `bench/package.json` declares them at the same version (glibc Linux x64 and arm64, macOS arm64) and `bun install` fetches the one for your host. Other hosts have no published 0.8.1 binding (Windows has one, not declared here), and `tests/microsandbox-native.test.ts` checks that the binding loads.

Rates (https://microsandbox.dev/pricing, 2026-11-24): Standard $0.048/vCPU-hour, $0.003/GiB-hour of memory and $0.0000625/GiB-hour of root disk ($0.220/hour at 4 vCPU / 8 GiB / 64 GiB); Shared $0.007, $0.000375 and $0.0000625 ($0.035/hour). Same-machine runs ask for `4:8192:64`; a restore keeps the snapshot's disk, so the runner forwards only `{ cpu, memoryMb }` on restores. The default size, 1 vCPU / 512 MiB, cannot run the realistic profiles.

Every allocation is journaled before the adapter sends it, through the adapter's attempt hooks:

- A create is journaled as `allocation-attempt` with the sandbox name it carries, its allocation marker and, for a restore, its snapshot and source. It becomes a `sandbox` entry when the adapter confirms the sandbox, and goes when the adapter fails with anything but `outcome_unknown` (nothing it made is left). Cleanup and recovery read an unresolved one by name: a sandbox carrying its marker on the right tier is deleted; anything else, a 404 included however old the attempt is, stays under review, and so do its restore's snapshot and source. A sandbox is forgotten only once an exact `GET /v1/sandboxes/{id}` reads 404 after its DELETE (Microsandbox deletes asynchronously), and only then are a restore's snapshot and source released.
- A preview's Service slug is journaled as `service` (`pending`) before `POST /v1/services`, marked `created` when the adapter confirms it, and dropped on a 409 or other refusal before the adapter tries another slug. The adapter's destroy deletes it with the sandbox. Cleanup and recovery never delete a journaled Service: Microsandbox deletes a Service only by its reusable slug, with no ID or precondition, so a slug re-made since the ownership check could be deleted in its place. One whose ownership is proven (it targets that sandbox's name, or is detached at a slug the journal does not show was taken) stays under review for you to delete. A 404 retires only a `created` entry; a `pending` one stays under review, since its create may still land. The adapter's own destroy has the same race, narrowed to a Service re-made at the slug, on the same account, between its timestamp check and its delete.
- A snapshot's name is journaled with its source and proof before the source is stopped. The confirmed managed ID replaces it; a refusal before any operation started drops it; anything else is settled through `GET /v1/snapshots/by-name/{name}` and `GET /v1/snapshot-operations`, and a 404 with no operation never clears it. A capture settled through its operation keeps the managed ID it found, journaled before the delete, so a name that is not indexed yet never drops a live snapshot.

Billing reads `GET /v1/billing/usage/sandbox` and `GET /v1/billing/usage` once for the run window, prices each per-sandbox daily row at its own `compute_type`'s rates and cross-checks `costs.workloads`. When `/v1/billing/usage` cannot be read, the rows are still rated and the note says the cross-check did not happen. A sandbox with neither is unavailable, never $0. Every cost is provisional (`complete: false`, low confidence): the rows meter running time only, so a stopped sandbox's disk is missing, and deletion is asynchronous. Neither tier is in the held-open idle diagnostic.

### Buddy

Buddy has no usage or billing API, so every Buddy cost is an estimate: the native tier the sandbox ran at (2 vCPU and 4 GB for the default `2x4`, verified on Buddy's Usage page) at $0.00024 per CPU-minute and per GB-minute, per started minute with a one-minute minimum. Buddy's GB are decimal, so the guest reports about 6.9% less memory than the tier name in GiB; the estimate prices the tier and the allocation check lists the gap as a caveat, and a Buddy `4x8` is never equal-spec with 8 GiB providers. Storage of used disk and snapshots ($0.00011/GB-hour) and the $29/month Pro plan are left out. Buddy has no hard lifetime, so realistic runs use no `timeoutMs`.

Snapshots are named by the run (`bench-<run>-<8 hex>`) and journaled with their source before `POST /sandboxes/{id}/snapshots`, under that name, since the ID comes only with the answer. The answer's ID replaces the pending name in the journal in one write, before the wait for `CREATED` and before any delete. A save whose answer was lost is settled by its exact name in the source's and the workspace's snapshot lists; a miss never drops it while the source exists and the save could still land (ten minutes), so an unsettled save keeps the entry, and its source, for `bench reap`. A delete checks the exact ID, the journaled name and the source in the snapshot's URL.

## Measure SDK overhead

`scripts/sdk-overhead.ts` measures what Sandbox SDK adds over the adapter and the provider's official SDK. It is separate from the published benchmark.

Each provider runs sequentially. `--sandboxes 5` means five SDK creates and five independent native creates, alternating SDK-first and native-first each iteration. The script destroys and checks each sandbox before continuing. All allocations carry a unique `sbx57` label or name. Boat is excluded.

The headline row is cold create → first exec: `createSandbox(provider)` followed immediately by `box.run("true")`, versus native create followed by native exec of `true`. The create floor row separates the native executable-sandbox create, the adapter's `provider.create()` inside the SDK create, and the complete `createSandbox()` call. Adapter and full-SDK create therefore refer to the same allocation. Create clocks include first-use lazy imports/client construction; later samples reuse the process. They measure fresh sandboxes, not fresh processes. Native boxd and Luxor clients reuse their gRPC transport, matching the adapters. Raw Daytona and Freestyle construct client wrappers per sample; their adapters retain the wrapper. Styne has no SDK of its own to compare with, so its floor is Styne's REST API through plain `fetch` (`POST /sandboxes`, `POST /sandboxes/{id}/commands`, `PUT /sandboxes/{id}/files`), and its init baseline imports nothing.

The first SDK sandbox also measures run, 1 KB write, read, edit, list and grep against the adapter, then against the native handle. Each operation has one unrecorded warm-up and `--n 10` recorded pairs, alternating call order. Native run and write use dedicated APIs when available. Native read/list/edit use `cat`, `ls -la` and `sed -i` through native exec; Luxor write uses native exec with base64. These shell floors differ from the SDK file API's result shapes, error checks and atomic edit semantics. Luxor's native handle invalidates its workspace cache, so the SDK/native phase reflects that state; the SDK/adapter phase runs first.

Init measures imports of the SDK root and provider subpath plus provider-factory construction, versus importing the native package alone. Each sample runs in a fresh Bun child process, timing inside the process and excluding process startup. This compares eager initialization; SDK factories load native clients lazily.

```sh
for k in E2B_API_KEY DAYTONA_API_KEY UPSTASH_BOX_API_KEY BOXD_API_KEY BOXD_ORG FREESTYLE_API_KEY TENKI_API_KEY SUPERSERVE_API_KEY; do
  export "$k=$(cat ~/.config/sandbox-bench/$k)"
done
timeout --signal=TERM --kill-after=90s 23m bun bench/scripts/sdk-overhead.ts \
  --providers e2b,daytona,upstash,boxd,freestyle,tenki,superserve \
  --sandboxes 5 --n 10 --out bench/results/overhead.json > bench/results/overhead.md
```

`--sdk <path>` selects another checkout's `packages/sdk`; it defaults to this checkout's. Build the selected SDK first with `bun run --cwd <path> build`. Both native modules and SDK modules resolve from that selected package. JSON records its Git commit, with `-dirty` for changes within `packages/sdk`, raw samples, both SDK operation timing series, medians, p90 and ranges. Delta is the difference of medians; cold/init metrics also retain paired-delta statistics. JSON checkpoints after each provider. A nonzero exit means an operation, provider or cleanup check failed.

Defaults match the adapters: E2B `base`, Daytona's default snapshot in target `us` (or `DAYTONA_TARGET`), durable Upstash Box, boxd's default image with isolation and auto-suspend/destroy disabled, Freestyle `freestyle/ubuntu` with idle timeout disabled, and Luxor's default image with inbound/outbound access. Superserve uses `sandbox-bench-node22-py311-1x1-pinned` on both sides; override E2B or Superserve with `--template provider=name`. Raw creates omit SDK workspace preparation and metadata setup, including Upstash's resume init command. Those extra guarantees are part of measured adapter overhead. Raw boxd readiness can include a native exec probe; Luxor uses native readiness rather than the adapter's stream-timeout fallback. Native labels and exact IDs are tracked separately from SDK discovery labels. Cleanup checks cannot prove the absence of an allocation whose create failed before returning its ID; inspect the unique run label/name if a provider reports an unknown outcome.

## Non-goals and documented limits

The harness does not try to do any of the following. Each is stated where it applies above; this list collects them.

Measurement:

- Proving a guest did its work. The CPU probe's checks reject wrong, stale and impossible replies, but the LCG has a closed form and a provider controls its guest's output.
- Trusting a dishonest guest's timers. The CPU overlap bound uses each guest's monotonic phase lengths: a guest that reports longer phases than it ran can inflate the bound. NTP slewing of a monotonic clock (at most 0.05%) is ignored.
- Modelling ambiguous CPU cohorts. A cohort whose proven overlap is under 0.8, whose exec overhead eats the bound, or whose evidence contradicts itself is left out, never corrected. Rows from before `exec` was recorded are invalid evidence.
- Using guest wall clocks. `clockDriftMs` is recorded and gates nothing.
- Removing confounders: network location, shared tenancy, image, package and filesystem caches, and Python version differences.
- Independent samples per workload. One sandbox serves several scenarios.
- Stable tails. p99 from 100 samples rests on the two slowest observations; a small pilot validates the harness and cannot rank providers.
- Comparing cold starts across the SBX-44 change to `run("true")`.
- Treating Docker `local` as a cloud product, or its shared filesystem as a dedicated disk.

Failure classes:

- Reading wording as a typed signal inside `cpu-burst` and `survival` cohorts. Only HTTP 429, or SDK code `quota` with no HTTP status, is an account limit there; every other status or code stays the provider's, so an account limit reported any other way counts against the provider.
- Keeping what a late heartbeat said. A reply or error after the deadline is a timeout, whatever its content.
- Treating `notRun` capabilities or account limits as provider failures.

Costs and budgets:

- Invoices. Costs and budgets are estimates; credits, subscriptions, transfer, retained snapshot storage, unstated creation fees and provider-side unknown-outcome charges are excluded, and none can be enforced by the local guard.
- Exact billing for allocation-priced providers. Upstash and boxd estimates are upper bounds; Modal's default track is a lower bound on its request.
- Account entitlements. Account caps are conservative admission settings, not verified limits.
- Bounding cleanup past a reserve. It is priced instead, to the first lookup that sees the sandbox gone.
- Exact stop times. A sandbox is priced until a lookup observes it gone, so the polling interval, rounding and charging cleanup separately from the iteration all over-report; nothing is subtracted for them.
- Pricing past the cutoff. The cutoff is taken just before the final report save, not at process exit. A sandbox never observed gone is an open liability priced to that cutoff; its cost keeps growing until it is reaped. On a provider with no exact lookup (Railway, AgentOS), or whose deleted sandboxes still read as live, every sandbox is reported this way.
- Currency conversion for ranking. EUR and USD stay separate; the 2 USD/EUR budget rate is admission-only.
- Local host costs.

Cleanup:

- Proving absence of an allocation whose create failed before returning an ID (`outcome_unknown`): inspect the provider account by run label.
- Proving absence from a failed ownership listing.
- Account-wide deletes. Reaping needs the run ID, and legacy snapshot entries without recorded proof need manual review.

## History

**2026-10-19, first v2 validation pilot** (run `sbx45-pilot-v2-fixed-20261019`). 566 observations: 530 measurements, 30 failures and 6 skips, across local, E2B, Daytona, Upstash, Boat, boxd, Freestyle and Tenki. Railway and Vercel were skipped without credentials. It was a harness check, not a ranking. It found:

- Daytona's snapshot wrapper lost the snapshot name when creation timed out. The harness now names Daytona snapshots before creating them and journals the source, so `reap` can find late snapshots.
- Daytona can report the host's 64 CPUs through `nproc`. The harness sizes workers and costs with `min(nproc, cpu.max quota)`.

SBX-44 later cut `run("true")` to one provider call. Measurements from before it are not comparable with later cold-start data.
