---
title: Memory
description: An in-process fake provider for tests. Files in a map, a small shell with handlers you can extend, fake preview URLs, and no network.
---

`memory()` is a provider that runs inside your own process. No machine starts. Files live in a map, commands run through a small built-in shell and handler functions you register, and preview URLs are fake. It exists for fast unit tests.

The full walkthrough is in [Testing with memory()](/guides/testing-with-memory).

## Installation

```package-install
npm i -D @opencoredev/sandbox-sdk
```

No other package is needed.

## Basic usage

```ts
import { createSandbox } from "@opencoredev/sandbox-sdk";
import { memory } from "@opencoredev/sandbox-sdk/memory";

await using box = await createSandbox(memory());
await box.files.write("hello.txt", "hi\n");
const result = await box.run("cat hello.txt && echo done");
console.log(result.stdout);
```

This prints `hi` and `done`.

## Configuration

```ts
import { createSandbox } from "@opencoredev/sandbox-sdk";
import { memory } from "@opencoredev/sandbox-sdk/memory";

const provider = memory({
  handlers: {
    npm: ({ args, stdout }) => {
      stdout(`npm ${args.join(" ")}: ok\n`);
      return 0;
    },
  },
});

await using box = await createSandbox(provider);
const result = await box.run("npm test");
console.log(result.stdout);
```

- `handlers` maps a program name to a function. The function gets the parsed `args`, `cwd`, `env`, `stdin`, an abort `signal`, `stdout` and `stderr` writers, and `files` to read, write, and list the fake files. It returns the exit code. A handler must stop when `signal` aborts, and must not touch the real world.
- `provider.register(name, handler)` adds a handler after creation.

These programs are built in: `echo`, `printf`, `cat`, `ls`, `pwd`, `true`, `false`, `sleep`, `exit`, and `printenv`. Your handlers replace a built-in with the same name. The shell understands quotes, `$VAR` for environment variables, `cd`, `export` (it sets the environment of the programs that follow, but `$VAR` expands before it runs), `;`, `&&`, `||`, `>` to write a file, and `>&2`. It is a small subset, not a full POSIX shell: there are no inline variable assignments, pipes, or subshells.

## Keys

Key mode is **exact**. Keys live in the provider instance, so they reset when the process exits.

## Previews

`box.preview(port)` returns a URL on the `memory.invalid` host. Assert on it, but don't fetch it.

## API reference

### `memory(options?)`

- `handlers?: Record<string, CommandHandler>`

Returns a provider with an extra `register(name, handler)` method. Each `memory()` call has its own files and processes. `box.native` is `{ files }`, the map that holds the fake file system.

## Limitations

- No real shell, git, terminals, or sockets. `box.git` and checks against a real HTTP server don't work.
- No pause or snapshots.
- `size` fails with `unsupported`, since there is no machine to size. `network` is accepted and recorded, since there is no network to restrict.
- The shell understands a small set of syntax: `;`, `&&`, `||`, `>`, and `>&2`. Anything else, such as pipes, `<`, `>>`, or a trailing `&`, fails with exit code 127 and a message naming the unsupported syntax. A program with no handler also exits 127.
- State is lost when the process exits.

Test those paths against [Local](/providers/local) instead.
